# Cross-device sync (v1)

This replaces the prototype's shared `localStorage['vida:sync']`, which only worked between tabs of one browser.

## Model
- **Postgres is authoritative.** Web, mobile and watch read and write the same tables through the same RPCs.
- **Stable ids.** Every synced row's `id` is generated by the client (UUID v4) when the user acts, so it is valid offline and identical on every device (ADR 0002).
- **Source attribution.** `devices` rows (`web|mobile|watch`) are referenced by `workout_sessions.device_id` and `workout_sets.device_id`. `client_recorded_at` keeps the device's own timestamp.

## Push: the outbox
`@vida/api-client` exposes `createOutbox(storage)`.

```
user taps "Serie hecha"
  → outbox.enqueue({kind:'record_set', input:{id: newId(), …}})   // persisted, status = pending
  → UI shows the set immediately with a "pending" marker
  → outbox.flush()  (on enqueue, on reconnect, on app start)
       ok              → status = confirmed
       NETWORK / 5xx   → stays pending, flush stops (order preserved), retried later
       business error  → status = failed (e.g. SESSION_CLOSED) → surfaced to the user
```

- Every queued operation is idempotent on its id, so a crash between "server committed" and "client marked confirmed" just causes a harmless replay.
- Storage must survive restarts: AsyncStorage or SQLite on mobile, Room or DataStore on Wear OS (Kotlin port of the same contract), IndexedDB on web.
- Pending vs confirmed is explicit (`OutboxEntry.status`). That matches the watch UI's "3 series sin enviar" state.

## Pull: keyset cursor
`sync.pull(table, cursor)` returns rows with `(updated_at, id) > cursor`, ordered, including tombstones (`deleted_at` not null). Clients keep one cursor per table:
`routines`, `routine_exercises`, `exercises`, `workout_sessions`, `workout_session_exercises`, `workout_sets`.

Supabase Realtime can later push "something changed" hints, so the web shows the watch's sets live. The pull stays the source of correctness.

## What works offline

| Operation | Offline | Notes |
| --- | --- | --- |
| Start a session | Yes | Send `exercises` with client ids (the snapshot), so sets can reference them before the first sync. |
| Record / edit set | Yes | `record_set` is idempotent. Edits made after confirmation are a plain `update`. |
| Pause / resume / complete / abandon | Yes | Replayed in order. Repeats are no-ops. |
| Edit routines | No (v1) | Requires `expected_version` against the server. Show "conectar para guardar". |
| Profile / preferences | No (v1) | Low frequency. |
| Account export / delete | No | Server-only. |

## Conflict rules

| Situation | Resolution |
| --- | --- |
| Phone and watch both start a workout | Partial unique index: the second `start_session` fails `ACTIVE_SESSION_EXISTS`. The client calls `workouts.active()` and joins the existing session. |
| Two devices record different sets | Both kept (append-only by id). `set_index` is display order only. |
| Same set sent twice | One row (id). |
| Pause from the watch arrives after "complete" from the phone | `INVALID_TRANSITION` → entry `failed`. The session stays completed (terminal states are final). |
| Set recorded offline *before* completion arrives *after* it | Accepted when `completed_at ≤ ended_at`. Rejected (`SESSION_CLOSED`) if recorded after completion or for an abandoned session. |
| Routine edited on two devices | Optimistic concurrency: the stale `save_routine` gets `VERSION_CONFLICT`. The client reloads and reapplies. |
| Routine edited after a session started | No conflict: the session uses its own snapshot (`workout_session_exercises`). |
| Anything else | Last write wins on server time (`updated_at`). |

## Recovery after restart
1. Load the outbox and `flush()`.
2. Call `workouts.active()` to resume the in-progress session (rest timer state is derived from the last set's `completed_at` and planned rest).
3. Pull with the stored cursors.
